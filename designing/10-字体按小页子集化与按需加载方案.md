# 10-字体按小页子集化与按需加载方案

> 状态：方案文档（待实施）
> 范围：先做 studio，验证可行后推广到其余 FullScreenPaging 页与滚动页

---

## 一、需求原话（用户）

> 我的想法是这样的，拿studio举例子：
>
> 进入Prologue的时候，只加载这个界面下出现的字体（单独子集化），然后在这一页内容加载好了以后再异步加载Symphony的字体，然后是Timeline的字体，最后是Epilogue，但是在直接通过链接进入某一页的时候就加载那个页面上的字体，再异步加载别的页面的，优先加载两侧的字体
>
> 当然Timeline的图片逻辑是前面Prologue加载好了以后就进入异步加载，和现在一样
>
> 你觉得这个逻辑行不行？会不会有什么问题？会不会因为反复拉取导致建立连接的时间比传输文件本身更长？

### 后续确认的决策

1. 预取节奏：**入口后全并行一批预取**（非串行逐个）
2. 版本化：**内容哈希**（文件名带内容 md5，而非时间/版本号后缀）
3. 范围：**先只做 studio**

## 二、现状分析

### 2.1 全局字体现状

- `src/css/fonts.css` 声明 5 个全局 @font-face（PMingLiU-TW / Huiwen-HKHei / PangMenZhengDao / cwTeXMing / Unifont），所有页面共用
- 子集文件：`public/font/*-subset.woff2`（pmingliu 50KB / hkhei 35KB / pangmenzhengdao 6KB / unifont 5KB / cwtexming 少量）
- 生成管线已存在：`font:subset:*` 脚本（glyphhanger + 字表）

### 2.2 studio 各小页字体映射（现状）

| 小页 | 组件 | 使用字体 |
|---|---|---|
| Prologue | FullScreenPhoto | PMingLiU + Unifont + cwTeXMing + PangMenZhengDao（标题动画 JS 轮换 4 种） |
| Symphony | Rainbow | PangMenZhengDao + Huiwen-HKHei + PMingLiU |
| Timeline | TimelinePlayer | Huiwen-HKHei（事件标题） |
| Epilogue | Footer | Huiwen-HKHei + PMingLiU |

### 2.3 核心问题

- 浏览器对 **visibility:hidden（隐藏小页）里的文本仍会下载字体**——所以现在 /studio 首屏一次性下载全部 5 个字体（~97KB），LCP/FCP 被字体卡在关键路径（此前 Lighthouse 实测 1.5–1.8s）
- 隐藏小页即使不显示，其字体也已下载，浪费首屏带宽

## 三、用户思路的解释与修正

### 3.1 逻辑是否成立？

**成立，方向正确**。每小页单独子集化 + 入口优先 + 邻页优先 + 激活后异步预取，能显著削减首屏字体负担。修正点如下。

### 3.2 修正 1：串行预取 → 全并行预取

原话是「Prologue 加载好后异步加载 Symphony，**然后** Timeline，**最后** Epilogue」——这是**串行**。串行会让每个 RTT 叠加（4G 每步 ~150ms，三步 ~450ms+），正是担心的「等待时间 > 传输时间」。

**修正**：入口节激活后，对其余各节字体**一次性全并行**发 `<link rel="preload" as="font" type="font/woff2" crossorigin>`。全部子集合计仅 ~20-30KB，一个 RTT 内拿完。

### 3.3 修正 2：连接时间真相

- **同一条 HTTP/2/3 连接**下，TLS 握手只发生一次（首个请求，与 HTML 同批），后续字体请求复用连接、多路复用，**不存在每字体握手**
- 每字体成本 ≈ 1 个 RTT + 传输（2-10KB）
- 「连接时间 > 传输时间」只在**串行逐个拉**时成立（每步叠一个 RTT）——全并行后此问题消失

### 3.4 修正 3：真正的「反复拉取」是缓存问题

- 同会话内导航不会重拉（浏览器内存/磁盘缓存）
- **跨会话**：当前 `/font/*` 无缓存头（nginx 只对 `/studio-history/` 设了 expires）→ 每次访问重拉
- **修正**：nginx 模板加 `/font/` 缓存头 + 文件名内容哈希（见下）

### 3.5 版本化：内容哈希（而非时间/版本号后缀）

| 方案 | 机制 | 问题 |
|---|---|---|
| **内容哈希（选定）** | 脚本算文件内容 md5 前 8 位，输出 `<font>-<section>-<hash8>.woff2`；内容不变 → 文件名不变（immutable 缓存命中）；内容变 → 文件名变（自动换新，浏览器必然拉新） | 零人工维护 |
| 时间/版本号后缀 | `-20260826` / `-v2` | 要人记得 bump，忘了就吃旧缓存 |

**使用方法与版本确定**：
- 「使用地点」由生成脚本输出的映射文件确定：`src/data/fontSections.ts`（节 → [{family, url}]），组件与预取脚本都从映射取 URL
- 「版本」由内容 md5 确定：脚本在生成时计算，文件名即版本；旧 hash 文件由脚本自动清理
- 配合 `Cache-Control: public, max-age=31536000, immutable`（文件名不变时永不重拉）

## 四、具体做法

### 4.1 新增文件

```
scripts/font-subsets.mjs                   # 子集生成管线（node 脚本）
src/css/nonGlobal/studioSectionFonts.css   # 生成的 @font-face 别名声明
src/data/fontSections.ts                   # 生成的映射：节 → [{family, url}]
src/utils/sectionFontPrefetch.ts           # 预取模块
```

`package.json` 新增命令：`font:subset:sections`。

### 4.2 阶段 1：子集生成管线（scripts/font-subsets.mjs）

1. 按 studio 四节收集文本：
   - Prologue：`studio.hero.*` + FullScreenPhoto `titleStates` 四组文案（JS 轮换字体用）+ 诗
   - Symphony：`departments.ts` + `game-start` 文案
   - Timeline：`timeline.ts` 事件列表（年份/标题/描述）
   - Epilogue：Footer 链接/版权/署名/busuanzi 标签
2. 每节每字体提取唯一字符 → 临时字表 → glyphhanger 生成 woff2 → 写入 `public/font/<font>-<section>-<hash8>.woff2`
3. 生成 `studioSectionFonts.css`：
   ```css
   @font-face {
       font-family: 'HKHei-Timeline';
       src: url('/font/hkhei-timeline-a1b2c3d4.woff2') format('woff2');
       font-display: swap;
   }
   /* 其余别名：PMingLiU-Prologue / Unifont-Prologue / cwTeXMing-Prologue /
      PangMenZhengDao-Prologue / PangMenZhengDao-Symphony / HKHei-Symphony /
      PMingLiU-Symphony / PMingLiU-Epilogue / HKHei-Epilogue */
   ```
4. 生成 `src/data/fontSections.ts`：Prologue→4 个 url、Symphony→3、Timeline→1、Epilogue→2
5. 输出日志：每节字节数、字符覆盖率
6. 清理 public/font 下旧 hash 残留

### 4.3 阶段 2：CSS 迁移 + 激活门控

- `pageAnimator.ts`：翻页完成时对当前 section 加/移 `.is-active`
- 各节字体引用改为 `别名, 全局, 系统` 三级回退（漏字时回退全局子集）：
  ```css
  font-family: 'HKHei-Timeline', 'Huiwen-HKHei', -apple-system, …;
  ```
- **别名只在激活节生效**：字体相关规则选择器加 `.is-active` 前缀（如 `#Timeline.is-active .event-title`）；未激活节用系统字体 → 零下载
- FullScreenPhoto 的 `titleStates`（JS 内联 fontFamily）改用节别名（Prologue 为初始激活节，加载即就位，scan 前不缺字）
- **保留全局 `fonts.css` 兜底**：无 JS 场景下首节（默认可见）仍能正常出字

### 4.4 阶段 3：预取（全并行）

`sectionFontPrefetch.ts`：
1. 读 `fontSections.ts` 映射
2. 入口节激活后，在 `load` / `requestIdleCallback` 时机触发
3. 对其余各节字体**一次性全并行**插入 preload link：
   ```html
   <link rel="preload" as="font" type="font/woff2" crossorigin href="/font/hkhei-timeline-a1b2c3d4.woff2">
   ```
   （必须带 `crossorigin`：@font-face 字体请求是 CORS 模式）
4. 直接 hash 入口（如 `#Timeline`）：入口节字体由 CSS 自然加载，其余节同样全并行预取；邻页/远页同批（全并行决策）
5. 可选：`navigator.connection?.saveData` 为 true 时跳过预取

在 `FullScreenPagingLayout` 的脚本中挂载一次。Timeline 图片预载逻辑保持现状，与字体预取完全独立、并行。

### 4.5 阶段 4：缓存头（部署侧）

`nginx-ssr.conf.j2` 增加：

```
location ^~ /font/ {
    expires 1y;
    add_header Cache-Control "public, immutable";
}
```

通过 `deploy.sh` 重新部署生效。

### 4.6 阶段 5：验证

- 生成日志：每节子集大小（预期 2-8KB）、字符覆盖率
- CDP / Lighthouse：
  - /studio 首屏字体请求**只有 Prologue 的 4 个**（合计 ~10-15KB，原 97KB）
  - 翻页到 Symphony 时，Timeline/Epilogue 字体已在预取队列
  - 字体响应带 immutable 缓存头
  - 直接进 `#Timeline`：Timeline 字体即时加载 + 其余并行预取
- `prefers-reduced-motion` / `saveData`：跳过预取
- 无 JS：全局兜底字体正常出字

## 六、风险与注意

- 切换小页时字体 swap 闪变：预取基本消除；用户快速翻页时短暂闪一下（子集几 KB，可接受）
- Symphony 的 PangMenZhengDao 仅在 hover 出现：激活时随该节子集一并预载
- 新增文案后必须重跑 `font:subset:sections`，否则漏字回退全局/系统字体
- 无 JS 场景：依赖全局 fonts.css 兜底，别名不生效（首节仍正常）
