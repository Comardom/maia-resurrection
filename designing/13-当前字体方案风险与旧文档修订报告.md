# 当前字体方案风险与旧文档修订报告

> 范围：只评估，不在本文中修改代码或旧文档
> 基准：当前工作区的字体子集、Header 独立字体和 studio 分页加载实现

## 1. 当前实现概况

当前有两套字体流程并存：

```text
旧流程：全局 fonts.css + 无 hash subset 文件
新流程：按使用点生成 hash woff2 + 生成 CSS/manifest
```

新流程当前覆盖：

```text
Header 站名
Prologue
Symphony
Epilogue
```

Timeline 当前使用系统字体，不在新字体 manifest 中。

旧流程仍被其他页面正文使用，因此目前不能直接删除。

## 2. 当前方案可能产生的问题

### 2.1 生成 CSS 不是稳定源码文件

Header 组件导入：

```astro
import '@/css/generated-header-font.css'
```

这个文件由生成脚本产生。如果执行：

```bash
pnpm dev
```

或直接执行：

```bash
astro dev
```

之前没有运行：

```bash
pnpm font:subset:studio
```

则开发服务器可能在解析 Header 时找不到 CSS 模块。

这是构建前置条件问题，不是字体文件加载问题。

当前实际应注意：

```text
先生成字体产物，再启动开发服务器或构建
```

### 2.2 Header 字体 CSS 与字体生成器耦合

Header 依赖生成器输出的固定文件名：

```text
src/css/generated-header-font.css
```

生成器还同时写入：

```text
src/css/generated-studio-fonts.css
src/data/generated/studioFontManifest.ts
```

其中任何生成步骤失败，都可能留下部分新文件和部分旧文件，导致 CSS、manifest、public/font 三者不一致。

例如：

```text
CSS 已更新
manifest 已更新
字体文件生成失败
```

这会在运行时形成 404。

### 2.3 生成器的字体文字映射仍然是手工维护

当前 `generate-studio-fonts.mjs` 使用硬编码文字数组：

```js
Prologue: {
    fonts: {
        pmingliu: [...],
        unifont: [...],
        pmzd: [...],
        cwtex: [...],
    },
}
```

这比“section 全量复制到所有字体”正确很多，但仍有维护风险：

- 数据文案修改后，字体配置可能没有同步修改
- 组件新增固定文案后，字表可能漏字
- CSS 中字体使用点改变后，生成器可能仍按旧归属生成
- 当前文件中的文字来源与实际数据文件存在重复维护

风险性质：

```text
不会扩大字体，但可能造成漏字和系统 fallback
```

### 2.4 Header 字表只覆盖站名，依赖当前设计边界

当前 Header 子集只包含：

```text
河南大学网站工作室
```

这符合已经确认的要求：

```text
只有站名使用独立 Huiwen
其他 Header 内容使用系统字体
```

风险在于以后有人给 Header 的其他文字添加：

```css
font-family: 'Huiwen-HKHei-Header'
```

但没有同步加入 Header 字表。此时新增文字会逐字 fallback。

### 2.5 旧全局 fonts.css 仍存在潜在泄漏

分页布局仍然导入：

```astro
import '/src/css/fonts.css'
```

旧 CSS 声明：

```text
PMingLiU-TW
Huiwen-HKHei
PangMenZhengDao
cwTeXMing
Unifont
```

虽然 studio 主要已经迁移到独立 alias，但任何残留旧 family 使用点都可能触发旧字体请求。

这会导致：

- 首屏额外请求旧字体
- Network 中同时出现新旧字体
- 测试时难以判断哪个字体真正生效
- 后续删除旧文件时产生页面回归

### 2.6 其他页面的旧流程依赖还没有完整清点

目前仍能看到旧 family 或旧 `fonts.css` 依赖的地方，包括：

```text
office
web
design
maintenance
ScrollablePageLayout
FullScreenPagingLayout
```

其中 Header 已经在组件 CSS 中切换到独立 alias，但其他页面正文是否仍需要全局字体，需要逐页确认。

因此当前不能直接删除：

```text
src/css/fonts.css
public/font/*-subset.woff2
font/*-words.txt
旧 font:subset:* 命令
```

### 2.7 旧命令和新命令容易被误用

当前同时存在：

```json
font:subset:all
font:subset:hk
font:subset:tw
font:subset:pmzd
font:subset:cwtex
font:subset:unifont
font:subset:studio
```

风险：

- 运行旧命令会更新旧无 hash 字体
- 运行新命令会更新新的 hash 字体
- 修改者可能不知道当前页面使用哪套文件
- 新旧文件同时存在时，缓存和 Network 结果容易混淆

### 2.8 `document.fonts.load()` 只表示加载请求，不保证视觉使用

当前分页器调用：

```ts
document.fonts.load(`1em "${alias}"`, sample)
```

它可以触发指定 alias 的加载，但不能保证：

- CSS selector 已经命中
- 元素最终使用该 alias
- 子集包含所有实际字符
- 字体加载完成后布局没有变化

所以浏览器验证必须同时检查：

```js
getComputedStyle(element).fontFamily
document.fonts.check(...)
Network 请求状态
```

### 2.9 preload 可能与 CSS 自然加载产生调度差异

后台预取使用动态 preload，优点是可以复用缓存；风险是：

- 某些浏览器可能忽略低优先级 preload
- preload 与后续 CSS 请求的 crossorigin 不一致时可能重复请求
- 用户快速翻页时，字体仍可能未完成
- 过多小请求在低端移动网络上可能产生调度竞争

当前采用全并行，符合已确认的设计，但应以真实 Network waterfall 验证，不应只根据代码推断。

### 2.10 旧页字体闪烁风险仍需浏览器回归

当前已经增加：

```text
is-active
is-entering
```

并且翻页时旧页继续保留 active。

这解决了之前“旧页仍在画面中但先失去字体”的主要问题。但仍需要测试：

- reduced motion 下的零时长动画
- 快速滚轮和 hashchange 同时发生
- 浏览器前进后退
- 字体尚未完成时继续操作
- 字体加载失败时的过渡

### 2.11 直接 hash 入口的初始化存在事件时序敏感性

当前 Timeline 仍有一个 `setTimeout(..., 0)` 兜底来检查 active 状态。它说明组件脚本和分页器之间仍存在初始化顺序依赖。

风险包括：

- 某个组件监听不到初始 `section:change`
- 直接进入中间页和普通进入行为不一致
- 后续组件复制这种模式，产生更多 timeout 补丁

### 2.12 字体文件删除策略可能影响长期缓存与回滚

生成器会清理旧 hash 字体，只保留当前生成结果。

优点：

- 工作区干净
- 不会积累无用文件

风险：

- 旧部署包若仍引用旧 hash，回滚时旧文件可能不存在
- CDN 或浏览器仍持有旧 HTML 时，旧 CSS URL 会 404
- 分阶段部署时，HTML、CSS、字体文件不是原子更新

如果部署不是整体替换，需要考虑保留旧 hash 一段时间，或者确保静态资源先于 HTML 切换。

### 2.13 nginx 缓存规则目前与本地 preview 表现不同

nginx 配置设置了：

```http
Cache-Control: public, max-age=31536000, immutable
```

但本地 Astro preview 通常返回：

```http
Cache-Control: public, max-age=0
```

因此本地测试不能直接代表线上缓存行为。需要分别测试：

- 本地无缓存
- 本地浏览器缓存
- 线上 nginx 缓存
- 部署更新后的旧缓存

## 3. 旧文档需要修改的地方

### 3.1 `designing/10-字体按小页子集化与按需加载方案.md`

这份文档是早期方案，以下内容需要修订。

#### 需要修订：manifest 包含 Header 的表述

旧文档曾把 Header 与 section 混在同一套映射中。当前正确边界是：

```text
Header 独立 CSS/资源
Prologue/Symphony/Epilogue 属于 studio section manifest
Timeline 不属于自定义字体 manifest
```

#### 需要修订：Timeline 字体映射

旧文档曾记录：

```text
Timeline = Huiwen-HKHei
```

根据当前确认，必须改为：

```text
Timeline 不使用任何自定义字体，全部使用系统字体
```

#### 需要修订：字体 fallback 表述

旧文档中仍有类似：

```text
section alias → 全局 Web Font → 系统字体
```

当前已明确不保留跨字体 fallback，至少应删除：

```text
cwTeXMing → PMingLiU
```

文档应该明确写成：

```text
每个 section alias → 系统字体 fallback
```

#### 需要修订：字表生成方式

旧文档中有按 section 收集文字的表述，容易被理解为：

```text
section 全部文字 → section 的每个字体
```

应替换为：

```text
字体使用点 → 实际文字 → 对应字体子集
```

#### 需要修订：字体文件大小预估

旧文档中的：

```text
每节 2-8KB
首屏约 10-15KB
```

属于未经最终生成验证的预估，应该删除或改为：

```text
以生成日志中的实际大小为准
中文字体文件大小与字形数量、字体结构有关，不能仅按字符数线性估计
```

#### 需要修订：开发命令名称

旧文档提到：

```text
font:subset:sections
```

当前实际命令是：

```bash
pnpm font:subset:studio
```

文档应统一命令名，避免复制错误。

#### 需要修订：Header 的加载位置

旧文档应明确：

```text
Header.astro 自己引入 Header 字体 CSS
```

而不是让 `studio.astro` 为 Header 提供字体定义。

### 3.2 `designing/11-字体子集化与按需加载架构.md`

这份文档已经比第 10 份更接近当前架构，但仍有以下需要修订之处。

#### 需要修订：当前状态描述

文档应区分：

```text
已实现的代码
已验证的构建行为
尚未完成的浏览器回归
尚未部署的 nginx 行为
```

不能把“构建通过”写成“浏览器所有页面验证通过”。

#### 需要修订：Header manifest 描述

当前 Header 已从 `studioFontManifest` 中删除。文档中所有仍然将 Header 作为该 manifest 顶层区域的内容都应更新为：

```text
Header 使用独立 CSS，不参与 section 预取
```

#### 需要修订：Timeline 内容

应统一为：

```text
Timeline 没有自定义字体
Timeline 不生成字表
Timeline 不生成字体文件
Timeline 不参与字体预取
```

#### 需要修订：启动前生成文件说明

文档应增加明确前置条件：

```bash
pnpm font:subset:studio
```

需要先运行该命令，确保生成的 CSS、manifest 和 woff2 存在，再启动开发服务器或构建。

#### 需要修订：硬编码字体文字映射的风险

当前生成器使用人工维护的字体文字数组。文档应记录：

```text
新增或修改页面文案后，需要同步审查对应字体使用点字表
```

## 4. 暂时不建议做的删除

当前不建议直接删除：

```text
src/css/fonts.css
font/*-words.txt
public/font/*-subset.woff2
package.json 的旧 font:subset:* 命令
```

原因：其他页面正文仍存在旧全局字体消费者。

正确删除条件：

1. 全仓库旧 family 引用清零。
2. 所有页面正文完成迁移或明确改用系统字体。
3. 所有 layout 不再 import `fonts.css`。
4. 构建产物不再出现旧 subset URL。
5. 线上旧 HTML 和缓存不会继续引用旧文件。
6. 回滚和分阶段部署策略已确认。
